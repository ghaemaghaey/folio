# Android UI Fixes — Scroll, Status Bar, Highlighter

## Issue 1: Scroll Not Smooth (No Momentum)

**Root cause:** `setupDragPan()` applies `touch-action: none` (via `.is-pannable` class) to ALL reading surfaces including `epubBook` and `scrollViewport`. This kills native browser touch scrolling and its built-in momentum/inertia. All scrolling is JS-driven `scrollTop` manipulation with no fling physics.

**Fix:** Remove `setupDragPan` from `epubBook`, `epubPages`, and `scrollViewport`. Only keep it on `pageViewport` (single-page PDF mode where drag-pan makes sense). The other surfaces should use native scrolling.

### File: `android/app/src/main/assets/www/main.js`

**Change 1** — Remove drag-pan from scroll/epub surfaces (around line 3289-3292):

```js
// BEFORE:
setupDragPan(el.pageViewport);
setupDragPan(el.scrollViewport);
setupDragPan(el.epubBook);
setupDragPan(el.epubPages);

// AFTER:
setupDragPan(el.pageViewport);
// scrollViewport, epubBook, epubPages use native scrolling (no drag-pan)
```

**Change 2** — Add `-webkit-overflow-scrolling: touch` and `overscroll-behavior-y: contain` to the scrolling containers in CSS to ensure momentum scrolling on Android WebView.

### File: `android/app/src/main/assets/www/style.css`

Add to `.scroll-viewport` (around line 1796):
```css
.scroll-viewport {
  -webkit-overflow-scrolling: touch;
  overscroll-behavior-y: contain;
}
```

Add to `.epub-viewport .epub-book` (around line 1625):
```css
.epub-viewport .epub-book {
  -webkit-overflow-scrolling: touch;
}
```

## Issue 2: Status Bar Overlap

**Root cause:** `MainActivity.kt` uses `WindowCompat.setDecorFitsSystemWindows(window, true)` which should push content below the status bar. But the FrameLayout wrapping the WebView doesn't propagate window insets to the WebView properly on some Android versions. The HTML has no `viewport-fit=cover` and no `env(safe-area-inset-top)`.

**Fix:** Change to edge-to-edge rendering with proper inset handling.

### File: `android/app/src/main/java/com/folio/reader/MainActivity.kt`

Change `setDecorFitsSystemWindows(window, true)` to `false` and apply window insets to the WebView:

```kotlin
WindowCompat.setDecorFitsSystemWindows(window, false)

// After setting up the WebView, apply window insets
ViewCompat.setOnApplyWindowInsetsListener(webView) { view, windowInsets ->
    val insets = windowInsets.getInsets(WindowInsetsCompat.Type.systemBars())
    view.setPadding(insets.left, insets.top, insets.right, insets.bottom)
    WindowInsetsCompat.CONSUMED
}
```

### File: `android/app/src/main/assets/www/index.html`

Add `viewport-fit=cover` to the meta viewport:
```html
<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover" />
```

### File: `android/app/src/main/assets/www/style.css`

Add safe-area padding to the library header:
```css
.lib-header {
  padding-top: max(var(--space-5), env(safe-area-inset-top));
}
```

## Issue 3: Highlighter Sticks When Dragging

**Root cause:** The `pointerdown/pointermove/pointerup` handlers on the guide don't have a `pointercancel` handler. If the browser cancels the pointer event (e.g., too many touch points, system gesture), `state.guideDragging` stays `true` and the guide appears stuck.

**Fix:** Add `pointercancel` handler that resets dragging state.

### File: `android/app/src/main/assets/www/main.js`

After the `pointerup` handler on the guide (around line 3278), add:

```js
el.guide?.addEventListener("pointercancel", () => {
  if (!state.guideDragging) return;
  state.guideDragging = false;
  persistGuide();
});
```

Also apply the same fix to the desktop version.
