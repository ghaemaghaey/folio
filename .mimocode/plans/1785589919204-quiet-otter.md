# Fix: Same-Device Restore Should Not Recalculate

## Problem
When opening a book on Android that was read on Android, the position jumps because the cross-device restore logic runs even for same-device positions. Only cross-device positions should recalculate.

## Root Cause
In `openBookId`, when `fetchAllDeviceProgress` returns 1 device (the current device), the code at lines 1575-1581 still sets `state.pendingCharOffset` and `savedScroll = 0`, triggering the cross-device char offset restore. This is wrong — local progress is already correct for same-device.

## Fix
Add a same-device check: if the server position comes from the current device, skip restore (local progress is already correct).

### Detection
Compare `serverDevice` (from the API response) with `getDeviceName()` (current device). If they match, it's same-device — use local progress directly.

### For EPUB:
- **Same device**: Skip server restore entirely. Local `savedPage`/`savedChapter`/`savedScroll` are already correct.
- **Different device**: Use char offset fraction (`co`) for cross-device matching.

### For PDF:
- **Same device**: Skip server restore entirely.
- **Different device**: Use page number (`p`) from the server.

### "Magic Number" on Server
The position format stored on the server is the "magic number":
- EPUB: `{c: chapter, co: charOffsetFraction, fp: textFingerprint}`
- PDF: `{p: page, c: chapter, s: subPage, sc: scrollRatio}`

The `co` (char offset fraction 0.0-1.0) IS the magic number — it's content-based, not viewport-based. It works across devices because it's a fraction of the chapter's text length, which is stable regardless of screen size or font.

### Files to modify:
- `android/app/src/main/assets/www/main.js` — openBookId
- `desktop/frontend/dist/main.js` — openBookId
